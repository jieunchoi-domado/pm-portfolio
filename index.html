종료일이 지났는데 상태가 ‘열림’인 일감이 남아 있습니다. 처리해야 화면이 해제됩니다. 해제 비용은 버튼 한 번입니다.

문제

영업일 22시 기준, 오늘이 완료일인데 아직 작업중인 일감이 75건이었습니다.
이 일감들은 내일이면 모두 오류 일감이 되어 Jira 일정의 신뢰도를 떨어뜨립니다.

조치

일감 관리에 대한 인터뷰를 진행했고, 대다수의 답변이 Jira에 접속해 내 일감을 확인하는 게 번거롭다는 반응이었습니다.
편의성 개선을 위해 봇이 각 담당자에게 메신저로 체크해야 할 일감과 원버튼 상태 변경을 보내는 기능을 지원했습니다.
하지만 30%의 절감밖에 체감하지 못했습니다.
그래서 사람들이 볼 수밖에 없는 출퇴근 앱에 결합했고, 배포 전 보안 이슈는 본부장님 설득과 CERT팀 협의로 풀었습니다.

결과

PM에게 필요한 강제성과 사용자에게 필요한 편의성을 함께 담은 Jira Plus로 발전시켜,
보안검수를 통과해 현재 프로젝트 내 파일럿을 운영하고 있습니다.

문제

오류 일감은 일감의 갱신을 놓쳐서 생깁니다.

프로젝트에서 정의하는 오류 일감은 3가지입니다.

  • 시작일이 지났는데 시작하지 않은 일감
  • 종료일이 지났는데 종료되지 않은 일감
  • 종료일이 미래인 일감

위 3가지 케이스 모두 날짜 혹은 상태를 갱신해주면 해결되는 문제입니다.
하지만 작업자는 Jira 진입조차 어려워합니다.

조치 1: 편의성 제공

Jira를 열지 않고도 상태를 바꿀 수 있게 했습니다

매일 당일 기준으로 시작 일감 / 종료 일감 / 오류 일감을 조회해
출/퇴근 시간에 맞춰 Teams DM으로 발송하도록 자동화 봇을 도입했습니다.
메시지 안에서 ‘작업 완료’·‘날짜 변경’을 원버튼으로 처리하도록 제공했습니다.

검증가설 실패

30%는 줄었지만, 70%가 남았습니다

오류 일감은 30% 감소했지만 여전히 70%가 남아 있습니다.
편의성은 작업자들이 일감 관리를 하게 하기 위한 필요조건이지 충분조건이 아니라는 것을 깨달았습니다.

조치 2: 구조적 개선

새로운 루틴을 학습시키지 않고, 필수 루틴에 기대었습니다.

전체 구성원이 반드시 누르는 출퇴근 앱에 연동했습니다.

  • 출근 버튼 클릭 시, 오늘 시작할 일감을 팝업으로 띄우고, 퇴근 버튼을 누르면 오늘 종료할 일감을 띄워줍니다.
  • 오류 일감은 가장 먼저 없앨 수 있도록 모든 팝업 전에 조회되도록 설계했습니다.

팝업 설정을 통해 일감 처리 전까지 화면 조작이 안 되도록 하는 기능도 추가했습니다.
결과적으로 오류 일감이 0에 수렴하는 구조가 됩니다.

배포 방안 문제

개별로 배포하면 빈틈이 생깁니다.

실 단위 배포 시, 구성원이 각자 앱을 내려받아야 합니다.
거부감을 최대한 줄여야 하는 일정 관리 앱의 경우, 이조차도 문제가 될 수 있습니다.
이 문제를 해결할 수 있는 것은 C레벨의 의지와 전사 차원의 설치라고 생각했습니다.

조치 3: 니즈 기반 설득

프로젝트 → PM실 → 전사 배포

팀장님의 컨펌 하에 실장님께 브리핑을 드렸습니다.
개별 설치를 거치지 않고 조직 전체에 한 번에 닿는 경로를 확보하기 위해,
PM실의 니즈와 Jira Plus를 연결 지어 전사 배포를 제안했습니다.

조치 4: 보안 이슈 해결

보안검수를 넘을 수 있도록 논의를 이끌었습니다.

배포 전 보안 이슈가 확인되었습니다.
팀장님과 함께 본부장님을 설득해, CERT팀이 우호적으로 검토할 수 있도록 논의를 이끌었습니다.
그 결과 보안검수를 모두 통과했습니다.

결론: Jira Plus

강제성과 편의성을 한 도구에 담다

긍정적 답변과 함께 PM실에서 테스트를 완료했습니다.
피드백까지 반영해 추가 수정을 진행했고, 직접 개발했습니다.
현재 프로젝트 내 파일럿을 운영하고 있습니다.

01 — 개발 진행 일정 관리

일정 변동을 사전에 찾아내
관리할 수 있는 환경을 만듭니다

일정 관리대내외 커뮤니케이션

200명 규모의 프로젝트에서 일정 변동을 쉽게 추적하고,
드라이하게 전달 가능하도록 구조를 바꿨습니다.

반복되던 상황

  • 공유 없이, 후행 프로세스를 고려하지 않은 일정 변경이 반복됨
  • 후행 부서 작업 직전에야 선행 작업이 끝나지 않았음을 확인해 일정 손실 발생
  • 리더 간 구두로 합의한 일정이 Jira에 반영되지 않아 F/U가 어려움
  • 이를 막기 위한 F/U에 PM이 일 평균 2시간 소요

문제 분석

일정 변경을 왜 늦게 알게 되는가?
  • 원인 1일정 변동을 공유하거나 감지할 소통 창구가 없었음
  • 원인 2일정 변경이 후행 부서 일정에 영향을 준다는 인식이 낮았음
구두로 합의한 일정은 어디에 기록되는가?
  • 원인 3Jira에 익숙하지 않은 리더들이 엑셀·Outlook 등으로 일정을 조정하고 있었음

조치

원인 1변경 일감 알리미
  • 전날 변경된 일감을 매일 11시 자동으로 알리는 알리미를 만들고, 유관 부서 리더를 모아 채널 개설
  • 봇이 드라이하게 변동을 알려, 리더끼리 쉽게 확인하고 질문할 수 있는 환경 제공
원인 2Jira Link · Automation
  • FS-Link로 프로세스를 연결하고, 선행 일감이 후행 부서 일감을 침범하면 알림이 가도록 자동화
원인 3Jira Structure 가이드
  • 공식 일정 관리 툴인 Structure를 쓰지 않던 리더 대상 인터뷰
  • 인터뷰 내용을 바탕으로 Structure 개선 및 가이드 제공
  • 일정 관련 소통을 모두 Structure로 진행하며 익숙해지도록 온보딩

2. Jira Link · Automation 제공

신규 기능 도입

변경 일감 채널로 인해 프로세스에 대한 인식이 올라오면서,
일감 변경 시, 후행 부서의 일감을 알고 싶다는 니즈가 생기기 시작했습니다.
적절한 시점에 도입을 준비 중이었던 일감 연결 기능을 Automation과 제공했습니다.
리더는 적극적으로 기능을 사용했고, PM은 일감 패트롤이 더 쉬워졌습니다.

제공 기능
  • 규칙 : 컨셉기획 → 원화 → 모델링 → 애니 → 이펙트 → 정식조립처럼 이어지는 일감을 FS(Finish-to-Start) 링크로 연결되도록 규칙 안내
  • Automation : 선행이 밀려 후행 일정을 넘으면, 선/후행 부서의 보고자에게 자동으로 알립니다
  • 가이드 : 위 내용을 문서화하여 제공했습니다.

3. 그래픽 7개 팀 Jira Structure 온보딩

Jira 일감 관리의 사각지대인 그래픽 직군 리더 인터뷰를 진행했습니다.
리더들이 팀마다 각기 다른 일정관리 툴을 사용하니, 각 팀의 일정이 공유되지 않았습니다.
툴을 쓰라고 공지하는 대신, 직군마다 실제로 보고 싶은 화면을 Structure에 팀별로 옮겨 주었습니다.

01

진단 · 누가 왜 안 쓰는가

Structure를 쓰지 않는 리더를 추려, 대신 무엇으로 일정을 관리하는지 확인했습니다.
대부분 엑셀/컨플루언스 문서였습니다.
이유는 “Jira 화면이 우리 팀이 보는 방식과 다르다”에 가까웠습니다.
도구의 문제가 아닌 뷰어의 문제로 정의했습니다.

02

인터뷰 · 팀별 니즈 취합

원화 / 모델링 / 애니 / 이펙트 / 배경 / 연출 / 라이팅
각 팀이 일정을 볼 때 어떤 단위로 묶고, 어떤 순서로 훑고, 무엇을 먼저 확인하는지 확인했습니다.
(2025.06)

03

제공 · 팀별 커스터마이징 Structure

니즈에 따라 Structure를 제공했고, 원하는 필터부터 기본적인 사용법 세미나를 진행했습니다.
세미나를 준비하며 Structure 사용 가이드를 만들어 배포했습니다.
세미나 이후에도 휘발되지 않을 수 있도록 기준을 문서로 남겼습니다.
(2025.07)

04

습관화 · 일정 이야기는 Structure 화면으로

가이드만으로는 습관이 바뀌지 않아서, 일정 관련 소통은 모두 Structure 화면을 띄워 놓고 진행했습니다.
엑셀 파일 대신 Structure 링크로 대화하다 보니, 리더들이 자연스럽게 Structure를 열어 확인하게 됐습니다.

*실제로 Structure 화면을 두고 모델링 일정을 재배치한 장면을 넣었습니다.

05

사용성 인터뷰 · 2차 개선

실제로 쓰면서 불편했던 점을 다시 인터뷰해 뷰를 한 번 더 고쳤습니다.
인터뷰 시, Link/SandBox 등 심화 기능에 대한 안내도 제공했습니다.
(2025.10)

06

정착 · 사각지대가 사라짐

모두 Jira를 기반으로 커뮤니케이션을 하다 보니, Jira의 일정이 가장 신뢰성이 있는 일정이 되었습니다.

  • PM의 일감 관리 공수도 일일 평균 2시간에서 15분으로 현저히 줄었고, 마일스톤 기준 일정 변경 F/U를 놓친 주요 일감이 0건으로 떨어졌습니다.
  • 프로젝트의 소통 비용도 절감되었습니다.
Structure 기반 일정 조율예시 이름으로 재현

02 — 부서 간 협업 · 프로세스 개선

일회성 이슈 해결이 아닌,
반복되지 않는 구조를 만듭니다.

부서 간 협업프로세스 개선

몬스터 스킬에 사용되는 프랍의 FX 일정의 지연을 감지했고,
그 사유에 대해 추적하다가 프로세스의 문제를 발견했습니다.

당시 프로세스에서 발견한 두 가지 문제

몬스터 스킬에 쓰이는 프랍 제작 프로세스입니다.
각 블록을 누르면 당시 제 생각의 흐름을 보실 수 있습니다.

빨간 블록의 단계를 문제 지점으로 판단했습니다.
클릭 시, 이유를 확인할 수 있습니다.
  1. 1몬스터 전투 컨셉 브리핑프랍 사용 여부 확정 · 배경 그래픽 리더 사전 노티
  2. 2몬스터 기획프랍 문서를 직접 작성
  3. 3몬스터 상세 브리핑배경 그래픽 리더 참석 · 서면으로 충분하면 생략
  4. 4일정 확인몬스터 조립·완료 시점 기준으로 논의
  5. 5제작 완료레벨 기획에 조립 지원 요청 → 최종 조립까지 F/U
원인 1 해결 방안 : 2단계
  • 니즈를 가진 몬스터 기획이 문서를 작성합니다.
  • 중간 전달자였던 레벨 기획 없이, 더 정확한 소통을 할 수 있습니다.
원인 2 해결 방안 : 1/4단계
  • 스킬 프랍 제작 일정을 몬스터 브리핑에서 확정하고 몬스터 일정 기준으로 논의합니다.
  • 배경 그래픽팀은 문서 확인 후, 참석이 필요 없을 경우 제작 일정만 짧게 논의하면 됩니다.
문제

몬스터 기획의 니즈를 레벨 기획이 대신 문서화하고, 레벨 브리핑에서 전달하고 있었습니다.

조치

흐름을 단계별로 뜯어 원인 두 곳을 특정하고, “몬스터 기획자는 프랍 조립을 못 한다”는 제약을 확인해 문서 작성과 조립을 분리했습니다.

결과

니즈를 가진 쪽이 직접 요청하고 몬스터 일정 기준으로 논의하는 구조로 바꿔,
두 문제를 한 번에 해소하고 프로세스 문서로 명문화했습니다.
이후 프로세스가 정착되는지 F/U까지 완료했습니다.

과정 자세히 보기제약 확인 · 주체별 액션 · 예외 처리
제약 확인

R&R을 조율하기 전에, 직군별로 가능한 업무의 범위를 확인했습니다.

  • 몬스터 기획자는 프랍 조립을 할 수 없었습니다.
  • 전부 몬스터 기획으로 옮기지 않고, 니즈를 문서로 쓰는 것까지만 몬스터 기획이 맡도록 했습니다.
  • 조립은 레벨 기획 측에 업무요청으로 지원받도록 정리했습니다.
부담 설계
  • 배경 그래픽 리더에게 몬스터 컨셉 회의 멘션은 리소스 요청에 대한 사전 노티일 뿐 참석할 필요가 없다고 명시했습니다.
  • 몬스터 상세 브리핑 시에도 서면으로 충분하면 프랍 제작 일정만 조율하도록 부담을 줄였습니다.
예외 처리
  • 적용 시점을 “오늘부터”로 명시했습니다.
  • 기획이 진행된 몬스터는 상세 브리핑 때 정식 요청이 가도록 안내했습니다.
  • 언제부터·누가·기존 건은 어떻게 처리할지에 대한 정리로 마무리했습니다.
주체변경된 액션설계 의도
몬스터 기획자 프랍 활용이 있으면 전투 컨셉·몬스터 상세 브리핑에 배경 그래픽 리더를 포함. 리소스 완료 시 레벨 기획에 조립 지원 요청 후 최종 조립까지 F/U 니즈 보유자가 직접 전달하도록 경로를 단축
배경 그래픽 리더 전투 컨셉 회의 멘션은 사전 노티
  • 참석 불필요. 상세 브리핑도 서면으로 충분하면 일정 확인만 진행
 프로세스를 추가하면서 참여 부담은 감소
몬스터 스킬 프랍 제작 일정을 몬스터 조립/완료 시점 기준으로 확인 레벨 프랍과 다른 기준선을 명시해 우선순위 밀림 차단
